# 产品说明

Cabbage 面向 AI Agent 和软件团队，用可执行门禁解决“文档存在但未完成、文档与代码脱节、变更缺少可追溯依据”三个问题。

## 用户与使用场景

| 用户 | 主要场景 | 获得的价值 |
| --- | --- | --- |
| 开发者与 AI Agent | 在实现前识别并完成所需文档 | 获得明确的下一阶段和阻塞原因 |
| 代码审查者 | 核对需求、设计、测试和发布证据 | 降低仅凭代码 diff 判断影响的成本 |
| 维护者 | 定义工作流、模板和 CI 策略 | 将文档规范转化为仓库内可执行规则 |
| 事故负责人 | 记录事故、复盘与纠正任务 | 保留从影响到整改的完整历史 |

## 核心能力

- `init`：初始化 `.cabbage/`、文档站点、CI 和可独立运行的 vendored CLI。
- `new`：按变更类型创建记录及初始文档。
- `impact`：维护产品、架构、API、数据库、安全、测试、部署、运维、数据和性能影响。
- `status` 与 `next`：显示阶段状态以及当前可执行阶段。
- `verify`：校验阶段产物合规性并记录内容与依赖签名。
- `sync`：自动将变更中的规范与设计增量同步沉淀到 `docs/` 对应当前状态目录。
- `gate`：在实现、合并和归档前检查所需阶段。
- `validate`：检查变更元数据和所有已激活文档。
- `archive`：校验门禁、自动同步规范并归档变更记录。
- `ci`：根据 Git diff 校验代码变更绑定、合并门禁和当前状态文档更新。
- `docs`：安装依赖、预览或构建 VuePress 文档站点。

## 支持的变更类型

当前内置八类工作流：`feature`、`architecture`、`bugfix`、`hotfix`、`refactor`、`migration`、`integration` 和 `incident`。每类工作流定义自己的阶段依赖，并可根据影响范围条件启用 API、数据库、安全、ADR 或发布文档。

## 阶段状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 阶段已启用但尚未验证 |
| `done` | 已通过验证，且记录签名与当前内容一致 |
| `stale` | 验证后产物、依赖、工作流或影响上下文发生变化 |
| `skipped` | 当前影响范围不启用该阶段 |

`verify` 不是手工勾选：它会检查依赖、frontmatter、必需标题、占位词、本地链接、Mermaid 围栏和实现任务清单。`.cabbage/changes/*/state.json` 属于 CLI 管理的状态，不应人工编辑。运行 `cabbage sync` 或 `cabbage archive` 时，系统会自动将已验证的规范增量同步到 `docs/` 全局文档。

## 产品约束

- 当前工作模式是仓库本地 CLI，不提供中心化服务或 Web 管理后台。
- 当前状态文档是否需要更新由影响字段与目录规则判断，具体内容仍由评审者确认。
- 分支保护和人工审核策略需要在代码托管平台配置，仓库内规则不能自行强制启用。
- Cabbage 不判断业务结论的真实性，也不替代测试、发布审批或事故指挥流程。

## 成功标准

一次变更应当满足：实现前置文档均为 `done`；代码变更绑定活跃变更记录；受影响的当前状态文档同步更新；合并前所有已激活阶段完成且无 `stale`；最终记录通过归档门禁保留。
